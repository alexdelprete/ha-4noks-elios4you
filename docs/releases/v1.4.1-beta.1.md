# Release v1.4.1-beta.1

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.4.1-beta.1/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.4.1-beta.1)

**Release Date:** 2026-10-02
**Type:** Beta release — Home Assistant deprecation alignment (patch). No functional changes.

---

## Overview

Maintenance pre-release. The integration was audited against the deprecation tables in the
Home Assistant core `dev` branch (2026.11.0.dev0, checked 2026-10-02): the deprecated-constant
tables, the `@deprecated_function` / `@deprecated_class` markers, and every
`report_usage(..., breaks_in_ha_version=...)` call in the helpers, config-entry and
entity-platform layers. One real hit was found and fixed; three small alignments with current
core conventions came along with it. No entity, `unique_id` or configuration changes.

## What's Changed

### Fixed

- **Deprecated `via_device` argument removed from device registration.** Since HA 2026.9,
  `device_registry.async_get_or_create` reports *any* use of the `via_device` keyword — the check
  only skips it when the argument is left out entirely, so the explicit `via_device=None` the
  integration passed logged a "deprecated `via_device` parameter" warning on every setup and
  reload. In HA 2027.8 the keyword is removed and the call would have raised `TypeError`, making
  the integration fail to set up. The argument is simply not passed any more: leaving it out
  already means "no via device" on every supported HA version, including the 2026.8.0 minimum.

### Changed

- The coordinator passes `config_entry=` explicitly to `DataUpdateCoordinator` instead of
  relying on HA's context variable. HA only reports the omission for core integrations, but the
  explicit form is the documented pattern.
- Platform `async_setup_entry` signatures use `AddConfigEntryEntitiesCallback`, the precise
  type for config-entry platforms, instead of the generic `AddEntitiesCallback`.
- `switch.py` imports `DeviceInfo` from `helpers.device_registry` (its canonical home, already
  used by the sensor and binary_sensor platforms) rather than `helpers.entity`.
- Dev tooling (template sync): ruff, ty, yamllint and pymarkdownlnt are pinned to the exact
  releases CI uses; `pytest-homeassistant-custom-component` bumped to 0.13.366.

## Audit notes

Checked and clean on the `dev` branch: device registry lookups (no `async_get_device`,
`suggested_area`, `deleted_devices`, `merge_*` or `add/remove_config_entry_id` usage), config
and options flows (no update listener, so `async_update_reload_and_abort` does not trigger the
2026.12 warning; no `show_advanced_options`), entity attributes (no `entity_id` or `group` set
on entities), the device-trigger symbols, and the unit/device-class constants.

**Deferred on purpose — voluptuous → probatio.** Since HA 2026.9.0, core validates schemas with
[`probatio`](https://pypi.org/project/probatio/) and only aliases `voluptuous` to it at
startup. `config_flow.py` and `device_trigger.py` still `import voluptuous as vol`; every name
they use is covered by the compatibility layer and nothing sets a removal date. Switching to
`import probatio as vol` would break the still-supported HA 2026.8.0, which ships no
`probatio`, so this waits until the minimum HA version is raised to 2026.9.0 or later.

## For beta testers

Nothing new to exercise functionally. The one thing worth confirming on HA 2026.9 or later:
after upgrading, the startup / reload log no longer contains the
"calls `device_registry.async_get_or_create` with a deprecated `via_device` parameter" warning
attributed to this integration.
