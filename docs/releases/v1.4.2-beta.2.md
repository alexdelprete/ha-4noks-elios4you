# Release v1.4.2-beta.2

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.4.2-beta.2/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.4.2-beta.2)

**Release Date:** 2026-10-19

**Type:** Beta release. Home Assistant now discovers Elios4you devices automatically, as a
*Discovered* card. Incremental notes: only what changed since v1.4.2-beta.1.

## What's Changed

### Added

- **Discovered card through DHCP.** The manifest declares DHCP matchers on the hostname the
  device sends in its DHCP requests (`E4U-<serial>`, captured from a real device as
  `E4U-5EA27546`), and the WiFi module's MAC prefix (`20:F8:5E`, Delta Electronics). Home
  Assistant's DHCP watcher starts a discovery flow when either matches. Other products use the
  same module, so the flow sends a unicast UDP-5002 probe and continues only if the device
  answers `HELLO <serial>`. Anything
  else is aborted silently, and no card is shown. This works on a fresh install, before the
  integration has any config entry.
- **Periodic UDP broadcast (integration discovery).** Once at least one device is configured,
  the integration broadcasts at startup and every 15 minutes. This finds additional devices,
  including devices with a static IP that the DHCP matcher never sees.
- **Confirm step.** A Discovered card asks only for a name. The connection is verified over
  telnet before the entry is created, using port 5001 and the default polling period.
- **Discovered devices follow IP changes.** When a configured device is discovered at a new IP
  address, the entry's host is updated. This only applies to devices configured by IP address.
  A configured hostname is never overwritten.

### Fixed

- **The add-integration form no longer suggests a device that is already configured.** Before
  this release, the UDP pre-fill used the first device that answered, which could be one you
  had already set up. Devices are now skipped when their host or serial already has a config
  entry, so a configured device that changed IP is still recognised.
- **`mac_address` was always empty** in the recovery script variables and in device trigger event
  data. The integration read it from the device's data, but the device never reports its MAC
  over telnet. The MAC is now learned by discovery and saved in the config entry, whichever way
  comes first:
  - **ARP lookup after the periodic broadcast.** The integration reads the device's MAC from the
    HA host's ARP table (`/proc/net/arp`), sending one unicast probe first if the entry is
    missing. On a shared LAN segment this fills the MAC of an already-configured device within
    15 minutes of startup. It was verified on a host-networked HA container, where it resolved
    `10.1.10.120 → 20:f8:5e:a2:75:46`.
  - **DHCP**: when Home Assistant sees the device's DHCP request.

  If neither applies, for example a routed subnet or bridge-mode Docker without DHCP visibility,
  the MAC stays empty. It's never guessed, and it's redacted in diagnostics.
- **A learned MAC is registered as the device's network connection.** It shows on the device
  page and enables a third DHCP matcher, `registered_devices`: any DHCP sighting of that MAC
  now reaches the integration, even if the hostname and MAC prefix matchers wouldn't match it.
  Home Assistant keeps connections separate per config entry, so the device is not merged with
  another integration's device that has the same MAC (e.g. a router tracker).

### Notes

- Devices are matched by serial: the serial in the UDP `HELLO` reply is the same one the
  integration reads over telnet and already uses as the config entry's unique ID. Existing
  installations need no migration.
- Quality scale: `discovery` and `discovery-update-info` move from *exempt* to *done*.
