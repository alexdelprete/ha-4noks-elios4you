# Release v1.4.0

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.4.0/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.4.0)

**Release Date:** 2026-09-09

**Type:** Minor release — Smart RC wireless accessory support, host auto-discovery, dynamic
entities. Everything since v1.3.1, consolidating three hardware-tested betas.

---

## Overview

v1.4.0 turns data the device was already sending — and previous versions threw away — into
first-class entities. Elios4you Smart units (or Elios4you + Red Cap module) report one
`DEVHA<n>` row per paired **Smart RC wireless accessory** (Smart Plug RC, Smart Switch RC,
Smart Relay RC, Power Reducer RC, Energy Meter RC) with live power, energy, signal and state:
this release exposes all of it, discovers the gateway on the network, and documents an
unusual amount of real-world device behaviour learned along the way.

Full credit to **@RickyReds**: the protocol reverse engineering and field mapping (reported
in #181, implemented in #182), the discovery-protocol find, and four rounds of real-hardware
beta testing — including a thunderstorm blackout that ended up validating the statistics
design better than any unit test could.

## What's Changed

### Added

- **Per-accessory entities.** Five sensors — Power (W), Energy (Wh, `total_increasing`),
  Signal (dBm, disabled by default), Name and ZigBee Device ID (diagnostic, disabled by
  default) — plus two binary sensors on a **new `binary_sensor` platform**: **Online**
  (`connectivity` device class) and **Relay**. The relay is a real physical contact; it is
  read-only because `@rel <n>` accessory addressing was tested on real hardware and the
  device silently ignores it.
- **Dynamic accessory entities.** Entities appear the moment their data first does — an
  accessory paired while Home Assistant runs, or one that was offline at the first poll
  coming online — and are removed automatically when an accessory is un-paired. No reload in
  either direction; both verified on hardware within a single poll cycle.
- **Per-slot generation with neutral naming.** Any number of accessories is supported
  without code changes, named "Accessory N". The Device ID diagnostic sensor exists so users
  with non-plug accessories can report their IDs — `81`/`0x0051` (Smart Plug RC) is the only
  confirmed value, and reports are welcome to make naming type-specific in a future release.
- **Host auto-discovery.** The device answers an undocumented discovery protocol on UDP port
  5002 (`Elios4you` → `HELLO <serial>`), found by capturing the official app's traffic. The
  add-integration form broadcasts a probe and pre-fills the host field. The UDP endpoint is
  non-exclusive — it answers even while the integration polls — so discovery can never
  disturb a running setup; manual entry always works. Verified on two networks and two
  firmware generations. Requires the HA process to have LAN broadcast access (HA OS,
  Supervised, host-networked containers; Docker *bridge* networking cannot broadcast to the
  LAN and the field simply stays empty).
- **ZigBee radio diagnostics**: Red Cap channel and PAN ID as disabled-by-default sensors —
  interference is the most common accessory complaint, and the channel tells you whether to
  blame neighbouring WiFi.

### Fixed

- **Offline accessories no longer report zeros** for power, energy and RSSI. A zero energy
  reading is interpreted by HA's statistics engine as a meter reset, which inflated the
  Energy dashboard on every offline/online cycle; 0 dBm reads as a very strong signal.
  Last-known values now persist while an accessory is offline; only Online and Relay reflect
  the offline row. This design has survived both a provoked counter reset and a real
  35-minute blackout with the statistics sum tracking the counter exactly — no phantom
  jumps.
- Signal sensor icon is `mdi:zigbee` (the accessory link is ZigBee, not WiFi).

### Changed

- **Minimum Home Assistant version raised to 2026.8.0** (was 2026.3.0). HACS will not offer
  this update on older installations.
- Replaced the deprecated `device_registry.async_get_device` API (warning since HA 2026.9,
  removal in HA 2027.8).
- New `CONTRIBUTING.md` centered on the devcontainer as the supported development path;
  `requirements-dev.txt` dropped in favor of `pyproject.toml` as the single dependency
  source. CI tests against HA 2026.9.0.

### Documentation

The README gained a Known Limitations set and a Smart RC Troubleshooting section built
entirely from real-hardware findings — worth reading before relying on accessories for
anything critical:

- Accessory counters are persisted only periodically: after a power loss the counter resumes
  from the last internal save (statistics adjust downward — understated, never inflated);
  re-pairing zeroes it entirely.
- **Relay is not a reachability indicator** — watch Online.
- Accessory relays cannot be switched via the local protocol; control stays in the 4-noks
  app.
- Entities are keyed by pairing slot (the protocol exposes no per-accessory serial): a
  replacement accessory inherits the slot's entities, history and stored preferences.
- ⚠️ The 4-noks app's **Save-settings opens the accessory relay and leaves it open**
  indefinitely, and the per-socket operating mode can **silently revert to Automatic** with
  no way to detect it in software.
- A "relay reports open but the load stays powered" state is fixable by factory reset; the
  app's Smart RC screen does not auto-refresh while open.

## Installation

**HACS**: Integration page → ⋮ → *Update* (or Redownload) → select 1.4.0 → restart Home
Assistant.

**Manual**: download `4noks_elios4you.zip` from this release, replace the
`config/custom_components/4noks_elios4you/` folder with its contents, and restart Home
Assistant.

## Breaking Changes

**None for installations upgrading from v1.3.1** — every accessory entity is new, and all
pre-existing entity `unique_id`s are unchanged. Note the raised HA minimum (2026.8.0).
