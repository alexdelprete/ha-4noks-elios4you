# Release v1.4.0-beta.1

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.4.0-beta.1/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.4.0-beta.1)

**Release Date:** 2026-09-04
**Type:** Beta release — Smart RC wireless accessory support, new binary_sensor platform,
dynamic entity creation.

---

## Overview

This is the first pre-release since v1.3.1 and the first release with **Smart RC wireless
accessory support**: Elios4you Smart units (or Elios4you + Red Cap module) report one `DEVHA<n>`
row per paired wireless accessory — Smart Plug RC, Smart Switch RC, Smart Relay RC, Power
Reducer RC, Energy Meter RC — carrying live power, energy, signal strength and state. Previous
versions discarded all of it; this release turns it into entities.

Full credit to **@RickyReds** for the protocol reverse engineering, the field mapping, the
initial implementation and the ongoing production testing (reported in #181, implemented
in #182).

## What's Changed

### Added

- **Per-accessory sensors**: Power (W), Energy (Wh, `total_increasing`), Signal (dBm, disabled
  by default), Name and ZigBee Device ID (diagnostic, disabled by default).
- **New `binary_sensor` platform** with per-accessory **Online** (`connectivity` device class)
  and **Relay** (disabled by default). The relay is a real physical contact in the accessory;
  it stays read-only for now — if the `@rel <n>` accessory-addressing hypothesis is confirmed
  on real hardware, it will become a controllable switch in a future release.
- **Dynamic entity creation at runtime**: entities appear the moment their data first does. An
  accessory paired after Home Assistant starts, or one that was offline at the first poll
  coming online, gets its entities on the next poll — no integration reload needed.
- **Per-slot generation with neutral naming**: any number of accessories is supported without
  code changes, named "Accessory N" because the Red Cap pairs more than plugs. The Device ID
  diagnostic sensor exists so users can report the ID of other accessory types —
  `81`/`0x0051` (Smart Plug RC) is the only one confirmed so far, and reports are welcome.

### Changed

- **Minimum Home Assistant version raised to 2026.8.0** (was 2026.3.0). HACS will not offer
  this update on older installations.
- Replaced the deprecated `device_registry.async_get_device` API (HA 2027.8 removal) with the
  `async_get_or_create` return value.
- New `CONTRIBUTING.md` centered on the devcontainer; `requirements-dev.txt` dropped in favor
  of `pyproject.toml` as the single dependency source. CI now tests against HA 2026.9.0.

### Fixed

- **Offline accessories no longer report zeros** for power, energy and RSSI. A zero energy
  reading is interpreted by HA's statistics engine as a meter reset, which inflated the Energy
  dashboard on every offline/online cycle; 0 dBm reads as a very strong signal. The last known
  values now persist while an accessory is offline; only Online and Relay reflect the offline
  row.
- Signal sensor icon is `mdi:zigbee` (the accessory link is ZigBee, not WiFi).

## For beta testers

The parser and sensor mapping have production hours on real hardware; the binary_sensor
platform and dynamic entity creation are new in this beta. Most valuable feedback:

1. **Accessory entities appear and update** (Power/Energy enabled by default; enable Signal,
   Relay and Device ID from the entity registry if you want them).
2. **Dynamic creation**: pair an accessory while HA is running — its entities should appear on
   the next poll without a reload.
3. **Offline behaviour**: power/energy/signal keep their last value while an accessory is
   offline (Online turns off); an accessory already offline at HA start gets those entities
   only when it first comes online — this is deliberate.
4. **Energy dashboard**: accessory Energy statistics should survive offline/online cycles
   without jumps.
5. **Device ID values** from accessories other than Smart Plug RC — please report them in #181's
   discussion or a new issue, so entity naming can become type-specific.

## Breaking Changes

**None for installations upgrading from v1.3.1** — every accessory entity is new, and all
pre-existing entity `unique_id`s are unchanged.

(Only if you were running the `main` branch between releases: accessory Online and Relay moved
from the sensor platform to the new binary_sensor platform, and display names changed from
"Smart Plug N …" to "Accessory N …". Remove the orphaned sensor entities from the entity
registry.)
