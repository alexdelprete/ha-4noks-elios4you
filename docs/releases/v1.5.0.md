# Release v1.5.0

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.5.0/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.5.0)

**Release Date:** 2026-10-20

**Type:** Minor release. Native discovery, a UDP liveness check that tells a deaf device from one
that's off the network, a working `mac_address`, and TCP resets that actually reach the device.

---

## Overview

Everything below is new since v1.4.1. It was tested in four pre-releases, published as
v1.4.2-beta.1 to beta.4, on two devices with different firmware and WiFi modules. The
version is 1.5.0 rather than 1.4.2 because the cycle added features, not just fixes.

There are no breaking changes, no entity changes and no migration. One thing you may notice after
upgrading: the integration reloads **once**, within about 15 minutes, when it first learns the
device's MAC address (see below).

## What's Changed

### Added

- **Discovered card.** A new Elios4you appears in **Settings › Devices & services** on its own;
  you don't need to open the add-integration form. Confirming the card asks only for a name. The
  connection is tested over telnet before the device is added, using port 5001 and the default
  polling period. The integration finds devices in two ways:
  - **DHCP.** Home Assistant's DHCP watcher matches on the hostname the device sends
    (`E4U-<serial>`), on its WiFi module's MAC prefix (`20:F8:5E`), or on a MAC already
    registered to one of your Elios4you devices. Other products use the same WiFi module, so
    every candidate must also answer the device's UDP-5002 discovery probe. Anything else is
    ignored silently. This works on a fresh install, before any device is configured.
  - **Periodic UDP broadcast.** Once at least one device is configured, the integration
    broadcasts at startup and every 15 minutes. This finds further devices, including ones with
    a static IP that DHCP never sees.
- **Devices follow IP changes.** When a configured device is discovered at a new IP address, its
  entry is updated. This only applies to devices configured by IP address. A configured hostname
  is never overwritten.
- **UDP liveness check on connection failure.** When the failures threshold is reached, the
  integration probes the device on UDP port 5002 (up to 3 attempts, 1.5 s each) before it fires
  device triggers, opens the repair issue or runs the recovery script.
  - **If the device answers**, it's on the network but its telnet service is wedged, the "deaf
    device" state. The failure is classified as `device_not_responding` even when the telnet
    connection itself timed out. Before this release, that case was reported as
    `device_unreachable`.
  - **A UDP answer can only upgrade** *unreachable* to *not responding*, never the reverse. If a
    firewall drops UDP 5002, behaviour is the same as before.
  - **The probe runs once per outage**, not on every failed poll.
- **A repair issue for the deaf-device state.** It says the device is online but telnet isn't
  responding, and that reconnecting its WiFi or power-cycling it fixes this. It's translated into
  all 10 languages.
- **New recovery script variables `failure_type` and `udp_reachable`**, so your script can pick
  the right action. The device trigger event data also includes `udp_reachable`, and the last
  probe result is in the diagnostics download.
- **The device's MAC address is registered** as its network connection, so it shows on the device
  page. A router integration that tracks the same MAC keeps its own separate device: Home
  Assistant keeps connections separate per integration, so nothing gets merged.

### Fixed

- **`mac_address` is no longer always empty.** The recovery script variable and the device event
  field were always empty, because the device never reports its MAC over telnet. The MAC is now
  learned by discovery and saved in the config entry, whichever way comes first:
  - from the Home Assistant host's ARP table, right after the periodic broadcast;
  - from the device's DHCP request.

  If HA and the device are on different subnets, or HA runs in bridge-mode Docker without DHCP
  visibility, it stays empty. It's never guessed, and it's redacted in diagnostics.
- **Forced aborts now send a TCP reset (RST).** The connection manager was always designed to
  drop a failed connection with a reset, so the device frees its socket slot even when its
  telnet task is wedged. Two bugs meant it never actually did, in any previous version:
  - the transport lookup returned nothing on telnetlib3 writers;
  - even once found, asyncio's `abort()` alone sends a normal FIN.

  Both are fixed. The socket now gets `SO_LINGER` set to 0 right before the abort, and packet
  captures in production show resets on the wire. On a device with periodic stalls, the resets
  also cut the timeouts during those stalls by about 3×: over 16 hours, from ~12.5 to ~3.6 per
  hour. No data was lost in either case, since every timed-out command is retried successfully.
- **The add-integration form no longer suggests a device that's already configured.** It used to
  pre-fill the first device that answered.
- **The README's Reconfigure section was wrong.** The device is identified by its serial, not its
  address, so changing the IP or hostname keeps all entities and history.

### Changed

- Quality scale: `discovery` and `discovery-update-info` are now *done*.

## Upgrade notes

- **One reload** happens within about 15 minutes of the first start, when the MAC is first saved.
  The entities are unavailable for under a second.
- **Recovery scripts:** existing scripts keep working. To act differently on a deaf device than
  on one that's off the network, use `failure_type` (`device_not_responding` or
  `device_unreachable`).
- **Discovery** needs Home Assistant to see the device's LAN traffic. HA OS, Supervised and
  host-networked containers are fine. In bridge-mode Docker, only the DHCP path can discover a
  device.
