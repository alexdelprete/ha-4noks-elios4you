# Release v1.4.2-beta.1

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.4.2-beta.1/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.4.2-beta.1)

**Release Date:** 2026-10-19

**Type:** Beta release. A UDP liveness check tells a device whose telnet service is wedged
apart from one that is off the network.

## What's Changed

### Added

- **UDP liveness check on connection failure.** When the failures threshold is reached, the
  integration probes the device on UDP port 5002 (the discovery protocol) before it fires device
  triggers, opens the repair issue or runs the recovery script. The probe tries up to 3 times,
  waiting 1.5 s for each answer.
  - If the device answers, it is on the network but its telnet service is wedged (the "deaf
    device" state). The failure is classified as `device_not_responding` even if the telnet
    connection itself timed out. Before this release, such a failure reported
    `device_unreachable`.
  - A UDP answer can only upgrade *unreachable* to *not responding*, never the reverse. If a
    firewall drops UDP 5002, behaviour is the same as before.
  - The probe runs once per outage, not on every failed poll.
- **New repair issue text for the deaf-device state.** It explains that the device is online but
  telnet is not responding, and that a WiFi reconnect or power cycle fixes it. The text is
  translated into all 10 languages. Both variants share one issue ID, so recovery clears either.
- **Recovery script variables `failure_type` and `udp_reachable`.** Scripts can now pick their
  action, for example restarting WiFi only when the device is still on the network.
- **`udp_reachable` in device trigger event data**, and the last probe result in the
  diagnostics download.

### Why UDP and not ping

The design comes from field evidence collected by @RickyReds (Refs #182). An external probe
captured 11 telnet outages across 3 independent events. UDP 5002 answered in all 11 while TCP
5001 timed out. ICMP timed out in 5 of the 11, so a ping-based check would have wrongly
reported a live device as gone. Two captures answered only on the second UDP attempt, which is
why the probe retries.
